# ADR 0006 — 클라이언트 사건 ID 기반 멱등 수집

- 상태: 승인
- 일자: 2026-08-30
- 관련: [02-ingest](../design/02-ingest.md), [ADR 0004](0004-parse-on-server.md)

## 배경

초기 Phase 2 구현은 `deviceId + packageName + body + receivedAt(분 단위)` 해시로
재전송을 판별했습니다. 이 방식은 서버 응답이 유실된 뒤 같은 원문을 다시 보낼 때는
중복을 잘 막지만, 같은 가맹점에서 같은 금액을 1분 안에 두 번 결제한 정상 사건까지
한 건으로 합칠 수 있습니다. 수집 단계의 오탐 중복 제거는 `RawMessage`를 복구 원천으로
삼는 설계와 맞지 않습니다.

또한 서버가 배치에 총 건수만 돌려주면 앱은 어떤 큐 행이 승인·중복·거부됐는지 알 수
없습니다. 거부 건을 함께 삭제하면 진단 원문이 사라지고, 모두 유지하면 영구히 같은
배치를 재전송합니다.

## 결정

1. Android는 캡처 사건마다 `clientMessageId`를 한 번 부여하고 로컬 큐에 함께 저장합니다.
   같은 OS 콜백의 재처리는 같은 ID를 만들며, 네트워크 재전송 동안 ID가 바뀌지 않습니다.
   알림 key·postTime이 같아도 본문이 바뀐 업데이트는 원문 유실을 피하려고 새 ID입니다.
2. 서버 멱등 키는 `deviceId + clientMessageId`로만 계산합니다. `RawMessage`에는
   `@@unique([deviceId, clientMessageId])`도 둡니다.
3. `/api/ingest`는 요약 건수와 함께 각 `clientMessageId`의
   `accepted | duplicate | rejected` 결과를 돌려줍니다.
4. 앱은 응답 ID 집합·중복·요약 건수를 모두 검증합니다. 승인·중복만 큐에서 지우고,
   거부는 원문과 사유를 로컬 `rejected_message` 테이블로 원자적으로 옮깁니다.
5. 기존 서버 원문은 마이그레이션에서 `legacy-<RawMessage.id>`를 부여해 보존하고,
   Android v1 큐 행에는 로컬 DB 마이그레이션에서 UUID를 부여합니다.

## 결과

- 동일 본문·동일 분의 정상 결제 두 건이 합쳐지지 않습니다.
- 저장 후 응답 유실과 적극적 재시도는 여전히 중복 행을 만들지 않습니다.
- 서버가 거부한 원문도 휴대폰에서 사라지지 않아 원인을 조사할 수 있습니다.
- 새 계약에는 `clientMessageId`가 필수입니다. 배포된 구버전 앱이 없었던 Phase 2
  실기기 검증 전 시점에 전환했으므로 호환 계층은 두지 않습니다.
- 알림과 SMS가 같은 결제를 각각 보내는 교차 채널 중복은 수집 단계에서 합치지 않습니다.
  둘 다 원문으로 보존하고 Phase 3 파서·취소/대사 단계에서 의미를 판단합니다.

## 기각한 대안

- **분 단위 내용 해시 유지**: 구현은 단순하지만 정상 사건 누락을 복구할 수 없습니다.
- **서버가 임의 ID 발급**: 응답이 유실되기 전에는 클라이언트가 그 ID를 알 수 없어 재전송
  상관관계를 만들지 못합니다.
- **거부 건 자동 폐기**: 독성 큐는 풀리지만 유일한 원문과 실패 원인을 잃습니다.
