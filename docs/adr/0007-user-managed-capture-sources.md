# ADR 0007 — 사용자 관리형 수집 대상과 복수 출처 원문 보존

- 상태: 승인
- 일자: 2026-08-30
- 관련: [08-android-app](../design/08-android-app.md), [02-ingest](../design/02-ingest.md), [ADR 0006](0006-client-event-idempotency.md)

## 배경

가족마다 사용하는 카드사 앱, 토스·카카오페이·네이버페이 같은 결제·자산 앱, 카카오
알림톡 채널, SMS 발신자가 다릅니다. 개발자가 패키지명과 발신자를 코드에 넣는 방식은
새 구성원마다 APK 수정·재배포가 필요하고, USB/ADB 조사를 전제로 해 실제 사용자 흐름이
될 수 없습니다.

한 결제는 카드사 앱과 결제·자산 앱 등 여러 경로에서 동시에 통지될 수도 있습니다.
수집 시 본문·시각이 비슷하다는 이유로 하나를 버리면 어느 원문이 더 정확한지 확인할
근거와 파서 복구 능력을 잃습니다. 반대로 Phase 3에서 그대로 거래를 여러 개 만들면
집계가 중복됩니다.

## 결정

1. 수집 대상은 각 사용자가 FamilyCard 설정 화면에서 직접 추가·삭제합니다. 설정은 해당
   폰의 private SharedPreferences에만 저장하고 자동 백업하지 않습니다.
2. 카드사 앱과 결제·자산 앱은 Android 시스템 앱 선택기로 고릅니다. FamilyCard가 설치 앱
   전체 목록을 직접 조회하거나 `QUERY_ALL_PACKAGES` 권한을 요청하지 않습니다. 사용자가
   선택한 패키지와 표시명만 받습니다.
3. 사용자가 앱을 `CARD_APP` 또는 `PAYMENT_APP`으로 분류합니다. 같은 패키지를 다시
   등록하면 새 분류로 교체합니다.
4. 카카오톡은 앱 전체로 등록할 수 없습니다. `com.kakao.talk` 알림 중 사용자가 등록한
   공식 채널 제목과 정확히 같은 것만 허용합니다. 기본 SMS 앱도 전체 앱으로 등록하지
   못하며, SMS 발신번호 또는 발신자 ID를 별도로 등록합니다.
5. 알림은 패키지·채널 판정 뒤에만 본문을 추출합니다. SMS는 발신자 판정 뒤에만 분할
   본문을 결합하고 거래 어휘를 검사합니다. 목록이 비었거나 설정 JSON이 손상되면 모두
   거부합니다.
6. 모든 원문에 `originKind`를 붙입니다. 전송 경로인 `source`와 별도로 카드사 앱,
   결제·자산 앱, 카카오 공식 채널, SMS 발신자를 구분합니다. 패키지명/발신자와 카카오
   제목도 원래 필드에 함께 보존합니다.
7. 같은 결제로 보이는 복수 출처 알림도 각기 다른 `clientMessageId`를 가진 `RawMessage`로
   전부 저장합니다. 수집 단계에서는 의미 중복을 판정하지 않습니다.
8. Phase 3은 실제 원문을 확보한 뒤 카드·금액·승인시각·가맹점·승인/취소 종류를 이용해
   복수 원문을 한 거래로 대사해야 합니다. 애매하면 합치지 않고 사람 확인 대상으로
   남깁니다. 어떤 경우에도 `RawMessage`를 삭제하지 않습니다. 현재의 원문 1건↔거래 1건
   스키마는 이 대사 모델을 구현하기 전에 반드시 재검토합니다.

## 결과

- 새 사용자는 USB 연결이나 개발자 도움 없이 본인이 쓰는 수집 경로를 구성할 수 있습니다.
- 토스·카카오페이·네이버페이 등 새 앱도 개발자 카탈로그 업데이트 없이 선택할 수 있습니다.
- `/raw`에서 동일 결제의 복수 알림이 어느 종류의 출처에서 왔는지 구분할 수 있습니다.
- 수집 누락을 피하면서도 Phase 3 집계 중복을 막을 근거가 보존됩니다.
- 대상을 삭제하면 이후 캡처만 멈춥니다. 이미 큐나 서버에 저장된 원문은 삭제되지 않습니다.

## 남는 위험과 완화

- 등록한 카드사/결제 앱의 **모든 알림 본문**이 수집됩니다. 등록 확인창에서 이 범위를
  명시하고 공식 금융 앱만 고르도록 안내합니다. 거래가 아닌 알림은 Phase 3에서
  `IGNORED`로 분류합니다.
- 카카오 알림은 OS가 제공하는 제목만으로 채널을 식별하므로, 일반 대화방 이름을 공식
  채널과 똑같이 만들면 구분할 수 없습니다. UI에서 이 한계를 경고하고 개인정보 canary로
  검증합니다.
- SMS 발신자는 위조될 수 있습니다. exact 발신자 일치에 더해 거래 어휘를 요구하지만,
  금융기관 공식 수치나 강한 발신자 인증을 뜻하지는 않습니다.
- `CARD_APP`/`PAYMENT_APP` 분류는 사용자의 선택입니다. 계산 신뢰 경계가 아니라 대사와
  진단을 위한 출처 메타데이터로 취급합니다.

## 기각한 대안

- **개발자 하드코딩 목록**: 사용자·앱 조합마다 코드 수정과 APK 재배포가 필요합니다.
- **USB/ADB로 패키지 조사**: 개발 진단에는 쓸 수 있어도 사용자 온보딩 흐름이 될 수 없습니다.
- **설치 앱 전체 조회**: 불필요하게 민감한 설치 목록을 앱이 다루며 광범위 패키지 가시성
  권한이 필요할 수 있습니다.
- **미등록 알림을 후보함에 임시 저장**: 후보를 만들기 위해 개인 알림 본문을 먼저 저장해야
  하므로 불변 규칙 4를 어깁니다.
- **수집 시 내용 기반 중복 제거**: 같은 금액·가맹점의 별도 정상 결제를 잃을 수 있고,
  실제 문구를 보기 전에는 안전한 의미 중복 규칙을 만들 수 없습니다.
