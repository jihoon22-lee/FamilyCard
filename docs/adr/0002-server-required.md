# ADR 0002 — 안드로이드 앱 단독이 아니라 서버를 둔다

- **상태**: 채택
- **일자**: 2026-08-10

## 배경

[ADR 0001](0001-collection-method.md)에서 알림 파싱을 택하면서, 안드로이드 앱이 필요해졌습니다. 그러자 자연스러운 질문이 나왔습니다.

> 굳이 수집기와 웹으로 나눌 필요 없이 안드로이드 앱 하나로 수집하고 내용 보고 다 하면 관리나 배포도 더 쉽지 않을까?

타당한 의문입니다. 구성요소가 하나면 관리할 것도 하나입니다.

## 문제

**카드 결제 알림은 각자 본인 폰에만 옵니다.**

아버지 카드 알림은 아버지 폰에, 어머니 카드 알림은 어머니 폰에 뜹니다. 폰 하나에 설치된 앱은 **그 사람 데이터만** 볼 수 있습니다.

이 프로젝트의 요구사항은 "가족별로 카드별 사용 금액과 실적을 정리해서 보는 것"입니다. 가족 N명의 데이터를 한 화면에 모으려면 **어딘가에서 합쳐야** 하고, 그 합류 지점이 서버입니다.

즉 서버는 선택이 아니라 요구사항에서 나오는 결론입니다.

## 검토한 대안

### A. 완전 단독 앱 (서버 없음)

각 폰이 독립적으로 동작하고, 합칠 때는 파일을 내보내 주고받습니다.

**탈락**: 매달 가족 전원이 파일을 내보내 한 사람에게 보내고, 그 사람이 취합해야 합니다. 자동화 목적에 정면으로 어긋납니다.

### B. 단독 앱 + 클라우드 백엔드 (Firebase 등)

앱이 전부 하되 데이터 동기화만 Firebase에 맡깁니다.

**탈락**: 금융 민감정보를 외부 서버에 두지 않는다는 방침과 어긋납니다. 그리고 결국 "앱 + 백엔드" 구조라 구성요소가 줄지도 않습니다 — 백엔드가 내 것이 아닐 뿐입니다.

### C. 한 사람 폰을 허브로

가족 폰들이 한 사람의 폰으로 데이터를 보냅니다.

**탈락**: 허브 폰이 꺼져 있거나 네트워크가 안 되면 수집이 멈춥니다. 결국 상시 켜져 있는 무언가가 필요한데, 그게 서버입니다.

### D. 앱 + 자가호스팅 서버 ← **채택**

## 배포 난이도에 대한 오해

"앱 하나가 관리·배포가 쉽다"는 직관은 실제로는 반대입니다.

| | 변경 시 배포 방법 |
|---|---|
| 서버 (파서·실적규칙·화면) | NAS에서 `docker compose pull && up -d` → **전원 즉시 반영** |
| 안드로이드 APK | 재빌드 → **가족 전원 폰에 각각 재설치 요청** |

Phase 3~4에서 정규식과 실적 규칙을 반복적으로 손보게 됩니다. 그게 앱에 있으면 그때마다 "앱 다시 깔아줘"를 가족 전원에게 부탁해야 합니다.

**APK가 배포하기 어려운 쪽이고, 서버가 쉬운 쪽입니다.**

## 결정

**안드로이드 앱 + 자가호스팅 서버 구조로 갑니다.**

그리고 이 결론에서 설계 원칙 하나가 따라 나옵니다.

> **자주 바뀌는 것은 전부 서버에 두고, APK는 한 번 깔면 다시 안 건드리게 만든다.**

이 원칙이 [ADR 0003](0003-webview-dashboard.md)(화면도 서버에)과 [ADR 0004](0004-parse-on-server.md)(파싱도 서버에)로 이어집니다.

## 결과

- 서버: Next.js + PostgreSQL, 집 NAS에 Docker로 배포
- 앱: 캡처와 전달만 담당하는 얇은 파이프
- 외부 접속은 Tailscale (공유기 포트포워딩 금지)
- 사용자가 관리할 것이 하나 늘어납니다 — NAS 운영, 백업, Tailscale 설정 → [admin-guide](../guide/admin-guide.md)로 부담을 낮춥니다

"앱 아이콘 하나로 다 본다"는 원래 요구는 [ADR 0003](0003-webview-dashboard.md)에서 서버를 유지한 채로 만족시킵니다.
