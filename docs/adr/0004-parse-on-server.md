# ADR 0004 — 파싱은 앱이 아니라 서버에서 한다

- **상태**: 채택
- **일자**: 2026-08-10

## 배경

안드로이드 앱이 카드 결제 알림을 캡처합니다. 그 텍스트에서 금액·가맹점·카드번호를 뽑는 작업을 **어디서** 할지 정해야 합니다.

앱에서 파싱하는 게 자연스러워 보입니다. 캡처한 자리에서 바로 처리하면 서버로는 정제된 데이터만 보내면 되고, 전송량도 줄어듭니다.

## 문제 두 가지

### 1. 카드사 알림 문구는 예고 없이 바뀐다

카드사 앱 업데이트 한 번에 `홍길동님`이 `홍*동님`이 되고, 구분자가 공백에서 줄바꿈으로 바뀝니다. 새 카드사를 추가할 일도 계속 생깁니다.

파싱이 앱에 있으면 **그때마다 APK를 재빌드하고 가족 전원에게 재설치를 부탁해야 합니다.** [ADR 0002](0002-server-required.md)에서 세운 원칙("APK는 한 번 깔면 다시 안 건드린다")과 정면으로 어긋납니다.

### 2. 과거 데이터를 고칠 수 없다

더 중요한 문제입니다.

앱이 파싱해서 결과만 보내면, 서버에는 **해석된 데이터만** 남습니다. 나중에 파싱 로직에 버그가 있었다는 걸 발견해도 이미 저장된 거래는 고칠 수 없습니다. 원본이 없으니까요.

3개월치 데이터가 미묘하게 틀렸다는 걸 알아차렸을 때, 손으로 고치거나 포기하는 것 외에 방법이 없습니다.

## 결정

**앱은 알림 원문을 그대로 서버에 보내고, 파싱은 전부 서버에서 합니다.**

```
앱:    캡처 → 원문 그대로 전송
서버:  원문 저장(영구) → 파싱 → 거래 생성
```

그리고 두 가지를 함께 정합니다.

### `RawMessage`는 영구 보관한다

수집한 원문은 **삭제하지 않습니다.** `Transaction`은 원문에서 언제든 재생성 가능한 파생 테이블로 취급합니다.

이게 **재파싱** 능력의 근거입니다. 규칙을 고치고 `POST /api/reparse`를 호출하면 과거 전체가 새 규칙으로 다시 처리됩니다. 3개월 뒤에 버그를 발견해도 전부 고칠 수 있습니다.

→ [불변 규칙 1](../../AGENTS.md)

### 파싱 규칙도 코드가 아니라 DB 데이터로

한 걸음 더 나아갑니다. 규칙이 서버 코드에 있으면 문구 변경 때마다 서버 배포가 필요한데, `ParserRule` 테이블에 두면 **웹 UI에서 정규식을 고치고 즉시 반영**됩니다.

새 카드사 추가에도 배포가 필요 없습니다.

## 트레이드오프

### 받아들인 비용

| 비용 | 판단 |
|---|---|
| 전송량 증가 (정제 데이터 대신 원문) | 알림 하나가 100바이트 남짓. 월 수백 건이면 무시 가능 |
| 서버에 원문이 쌓임 | 자가호스팅이라 외부 노출 없음. 오히려 감사 추적에 유리 |
| 파싱 실패를 서버에서 다뤄야 함 | 어차피 사람의 개입이 필요한 일. 큐 UI를 만들면 됨 |
| 앱이 자기 데이터를 해석하지 못함 | 앱은 어차피 WebView로 서버 화면을 보므로 무관 |

### 얻은 것

- 규칙 수정이 배포 없이 즉시 반영
- **과거 데이터 소급 수정** — 이 시스템의 핵심 복구 수단
- 파싱 실패 건이 원문과 함께 남아 나중에 해결 가능
- 앱이 단순해져서 버그가 날 여지가 줄어듦

## 결과

- `RawMessage`에 `parseStatus` 상태 기계가 생깁니다 (`PENDING → PARSED / FAILED / NEEDS_CARD / IGNORED`)
- 미확정 큐 UI가 필요합니다 — 실패 건을 사람이 처리하는 화면
- 재파싱 시 **사람이 손으로 고친 내용을 덮어쓰지 않아야** 합니다 → `Transaction.isManuallyEdited`
- 재파싱 시 취소가 **이중 차감되지 않아야** 합니다 → [05-cancellation](../design/05-cancellation.md)
