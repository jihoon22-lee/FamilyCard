# 로드맵

## 전체 흐름

```
Phase 0  문서 · CI/CD
   │
Phase 1  스캐폴딩              Next.js + Prisma + Auth + scope 계층   ← 현재
   │
Phase 2  수집 파이프라인        /api/ingest + 안드로이드 앱
   │                          ★ 여기서 실제 알림 원문이 쌓인다
   │
Phase 3  파서 + 카드 매칭       ← 쌓인 원문을 보고 규칙 작성
   │
Phase 4  실적 엔진             이 프로젝트의 목표
   │
Phase 5  관리자 가족 대시보드    scope=FAMILY 첫 사용처
   │
Phase 6  보정 · 운영            명세서 대사 · 알림 · 백업
   │
Phase 7  실사용 검증 · 안정화   한 사이클 이상 실사용 후 v1.0.0
```

## 의존관계

| Phase | 선행 조건 | 이유 |
|---|---|---|
| 1 | 0 | 문서·CI 없이 코드부터 쌓으면 세션이 끊길 때 이어받기 어려움 |
| 2 | 1 | 스키마와 인증이 있어야 수집 엔드포인트를 만들 수 있음 |
| **3** | **2 완주** | **실제 알림 문구가 있어야 파서를 쓸 수 있음 (아래 참고)** |
| 4 | 3 | 거래가 카드에 정확히 붙어야 실적 산정이 의미 있음 |
| 5 | 4 | 가족 매트릭스에 실적 달성률이 들어감 |
| 6 | 3 | 명세서 대사는 파싱된 거래와 대조하는 것 |
| 7 | 6 | 실사용 데이터가 한 사이클 쌓여야 검증 가능 |

### Phase 2 → 3 순서를 지켜야 하는 이유

**실제 카드사 알림 문구를 보기 전에 정규식을 짜지 않습니다.**

카드사별 알림 문구는 검색으로 알 수 있는 것이 아닙니다. 같은 카드사도 앱 푸시·SMS·알림톡의 형식이 다르고, 카드 종류에 따라서도 다릅니다. 추측으로 규칙을 만들면 실물이 도착했을 때 전부 다시 써야 합니다.

**Phase 2의 산출물인 "쌓인 원문"이 Phase 3의 입력입니다.**

Phase 2에서는 파싱을 아예 하지 않고 원문만 저장합니다. 가족이 며칠 카드를 쓰면 각 카드사의 실제 문구가 모입니다.

## 버전 태그

Phase 완료 시 태그를 끊습니다. 태그를 push하면 CD가 GHCR 이미지와 릴리스 APK를 만듭니다.

| 태그 | Phase | 그 시점에 되는 것 |
|---|---|---|
| `v0.1.0` | 1 | 로그인해서 빈 대시보드를 볼 수 있음 |
| `v0.2.0` | 2 | 앱이 결제 알림을 캡처해 서버에 쌓음 |
| `v0.3.0` | 3 | 카드별 월간 사용금액이 보임 |
| `v0.4.0` | 4 | **카드별 실적 달성 추정치가 보임** |
| `v0.5.0` | 5 | 관리자가 가족 전체를 봄 |
| `v0.6.0` | 6 | 명세서 대사로 정확도 보정 |
| `v1.0.0` | 7 | 한 사이클 이상 실사용 검증을 마쳐 숫자를 신뢰할 수 있음 |

`v0.4.0`이 실질적인 목표 지점입니다. 원래 요구("가족별로 카드별 사용 금액과 실적을 정리해서 보고 싶다") 중 개인 시점 부분이 여기서 완성됩니다.

## Phase별 완료 기준

각 Phase의 상세 작업 항목은 `phase-N.md`에 있습니다. 여기서는 "무엇이 되면 끝인가"만 적습니다.

### [Phase 0 — 문서 · CI/CD](phase-0.md)
문서 일체가 작성되고 CI가 초록. **신규 세션이 `AGENTS.md` + `HANDOFF.md`만 읽고 다음 작업을 시작할 수 있으면** 완료.

### [Phase 1 — 스캐폴딩](phase-1.md)
`docker compose up` 후 로그인해서 빈 대시보드가 뜸. 세션에 `role`/`scope`가 담기고 `visibleMemberIds()`가 동작. CI가 실제 코드를 검증.

### [Phase 2 — 수집 파이프라인](phase-2.md)
실기기에 APK를 깔고 실제 결제를 하면 서버에 원문이 쌓임. 기내모드 결제도 복구 후 자동 업로드. **카카오톡 일반 대화는 서버에 안 올라감.**

### [Phase 3 — 파서 + 카드 매칭](phase-3.md)
쌓인 원문이 거래로 변환되고 카드별 월간 사용금액이 보임. 미확정 큐에서 사람이 개입 가능. 재파싱 동작.

### [Phase 4 — 실적 엔진](phase-4.md)
카드별 실적 진행률과 "N원 더 쓰면 달성"이 보임. **실제 카드사 앱 수치와 대조해 오차를 튜닝한 상태.**

### [Phase 5 — 관리자 대시보드](phase-5.md)
관리자가 웹에서 가족×카드 매트릭스를 봄. **권한 테스트 전부 통과** — 특히 ADMIN 폰 앱에서 본인 것만 보이는지.

### [Phase 6 — 보정 · 운영](phase-6.md)
명세서 엑셀 업로드로 누락 건이 리포트됨. 수집기 무응답 감지. 백업 자동화.

### [Phase 7 — 실사용 검증 · 안정화](phase-7.md)
전 카드에 대해 한 사이클 이상 카드사 앱 수치와 대조를 마침. 백업에서 실제로 복구해봄. 데이터가 쌓인 상태에서 성능을 확인함. **이걸 마쳐야 v1.0.0.**

## 각 Phase 종료 시 절차

1. `docs/plan/phase-N.md` 체크박스 갱신
2. `CHANGELOG.md`에 버전 섹션 추가
3. `docs/HANDOFF.md` 갱신 — 다음 Phase의 첫 작업까지 적어둘 것
4. 커밋 → 푸시 → 태그

→ [AGENTS.md 세션 종료 절차](../../AGENTS.md)

## 일정에 대해

일정을 못 박지 않습니다. 이 프로젝트에는 **바깥 사정에 달린 대기 시간**이 끼어 있습니다.

- Phase 2 → 3: 가족이 며칠 카드를 써야 알림 문구가 모입니다
- Phase 4: 실적 검증은 **한 사이클(한 달)을 기다려야** 실제 수치와 대조할 수 있습니다
- Phase 7: 전 카드 대조와 실사용 피드백 반영은 **한 달 이상의 실사용 대기**를 전제로 합니다. 기능을 다 만든 뒤에도 v1.0.0까지는 시간이 걸립니다

Phase 4의 실적 정확도는 첫 달에 맞추기 어렵습니다. 한두 달 쓰면서 제외 규칙을 조정해가는 과정을 전제로 설계했습니다. → [06-benefit-engine](../design/06-benefit-engine.md)
