# Phase 6 — 정확도 보정 및 운영

> 버전 태그: `v0.6.0`

## 목표

알림 파싱의 구조적 한계를 메우고, 장기 운영 가능한 상태로 만듭니다.

## 완료 기준

- 명세서 엑셀을 올리면 누락·불일치 건이 정확히 리포트됨
- 수집기가 조용히 멈춘 것을 감지할 수 있음
- 백업이 자동으로 돌고 복구 절차가 문서화됨

## 작업

### 명세서 대사 (reconciliation) ★ 핵심
- [ ] [통합 실행 계획](post-collection-execution.md)의 비기기 원문 provenance 결정 확인
  - `RawMessage.deviceId`를 채우기 위한 가짜 Device 생성 금지
  - 구성원·업로드 파일·명세서 행의 관계와 원본 파일 보관 방식을 ADR로 확정
- [ ] 카드사 이용내역 엑셀/CSV 업로드
- [ ] 카드사별 컬럼 매핑 (카드사마다 형식이 다름 → 매핑 규칙을 데이터로)
- [ ] `RawMessage.source = STATEMENT`로 저장 (원문 보관 원칙 유지)
- [ ] 수집 데이터와 대조
  - **명세서에는 있는데 우리에게 없음** → 누락 (알림을 못 받음)
  - **우리에게는 있는데 명세서에 없음** → 취소됐거나 잘못 파싱됨
  - **금액 불일치** → 부분취소 누락 또는 해외 환율 확정
- [ ] 대사 결과 화면 — 차이 목록 + 일괄 보정
- [ ] 보정 시 `isManuallyEdited = true` (재파싱이 덮어쓰지 않게)

### 알림
- [ ] 실적 미달 임박 알림 (사이클 종료 N일 전, 달성률 M% 미만)
- [ ] 실적이 **달성 → 미달로 떨어졌을 때** (취소 소급 반영)
- [ ] 전달 수단 — 웹 푸시 또는 텔레그램 봇
  - 집 서버가 밖에서 안 보일 수 있으므로 텔레그램이 실용적

### 수집기 무응답 감지
- [ ] `Device.lastSeenAt` 기준 `DEVICE_SILENCE_WARN_DAYS` 초과 시 경고
- [ ] 대시보드 + 관리자 화면에 표시
- [ ] 알림 발송 (위 알림 채널 재사용)
- [ ] 원인 안내 — "알림 권한이 꺼졌거나 배터리 최적화에 걸렸을 수 있습니다"

### 백업 · 운영
- [ ] `pg_dump` 자동 백업 (cron 또는 systemd timer)
- [ ] 백업 보존 정책 (일 7 · 주 4 · 월 12)
- [ ] **복구 절차 문서화 + 실제로 한 번 복구해보기** ★
- [ ] 디스크 용량 모니터링
- [ ] NAS 자동 업데이트 (Watchtower 또는 systemd timer) 설정 안내

## 주의

### 대사는 알림 파싱의 안전망이다

이 프로젝트는 카드사 API가 아니라 알림을 읽습니다. 아무리 파서를 잘 만들어도 **애초에 알림이 안 온 건은 알 방법이 없습니다.**

- 카드사 앱의 최소 금액 임계값에 걸린 소액 결제
- 알림 권한이 꺼져 있던 기간
- 앱 설치 전 결제

명세서 대사가 유일하게 이걸 잡습니다. 월 1회만 해도 정확도가 크게 올라갑니다.

### 복구를 실제로 해보기

★ 표시한 항목이 중요합니다. 백업 스크립트가 돈다는 것과 그 백업으로 복구가 된다는 것은 다릅니다. 한 번도 복구해보지 않은 백업은 백업이 아닙니다.

빈 DB에 덤프를 복원하고 앱이 정상 동작하는지 확인하세요.

### 알림 채널로 텔레그램이 실용적인 이유

웹 푸시는 사용자가 서버 페이지를 열어둬야 하는데, 집 서버는 Tailscale이 꺼져 있으면 접근이 안 됩니다. 텔레그램 봇은 서버에서 밖으로 나가는 요청이라 그 제약을 받지 않습니다.
