# 알림 수집 이후 통합 실행 계획

> 범위: Phase 2 수집 종료 판정부터 Phase 7 `v1.0.0`까지
>
> 이 문서는 단계 사이의 **순서·진입 게이트·PR 단위**를 정의합니다. 세부 기능 체크리스트는
> 각 `phase-N.md`, 설계의 이유와 알고리즘은 `docs/design/` 및 `docs/adr/`가 기준입니다.

## 왜 별도 실행 계획이 필요한가

Phase별 기능 목록만 보고 바로 파서 정규식을 쓰면 다음 세 가지 실수가 생기기 쉽습니다.

1. 며칠 지났다는 이유만으로 표본이 부족한데 Phase 3을 시작함
2. 실제 금융 원문을 테스트·이슈·문서로 복사해 개인정보를 Git에 남김
3. 현재 `RawMessage` 1건↔`Transaction` 1건 관계를 먼저 바꾸지 않고 파싱해, 카드사 앱과
   결제 앱의 같은 결제를 두 번 집계함

따라서 “수집 기간”이 아니라 **필요한 문구 변형과 반례가 확보됐는지**로 시작 시점을
판정하고, Phase 3을 작은 검증 단위로 나눕니다.

## 전체 흐름

```text
현재: 원문 계속 수집
        │
        ▼
Gate C0  Phase 2 종료 가능 여부 판정
        │  개인정보 canary · 수집 복구 · 문구/출처 커버리지 · 서명 배포
        ▼
v0.2.0  수집 파이프라인 기준선 고정
        │
        ▼
P3-A    보안 원문 분석 · 정답셋 · ADR
        │
P3-B    복수 원문↔의미 거래 스키마와 보존형 migration
        │
P3-C/D  순수 파서 · 카드 등록/매칭
        │
P3-E/F  복수 출처 의미 대사 · 취소
        │
P3-G/H  미확정 큐 · dry-run 재파싱 · 카드별 사용금액
        ▼
v0.3.0
        │
        ▼
Phase 4 실적 추정 엔진·한 카드 한 사이클 대조       → v0.4.0
Phase 5 가족 대시보드·scope 공격 회귀 테스트         → v0.5.0
Phase 6 명세서 대사·무응답 감지·백업 자동화          → v0.6.0
Phase 7 전 카드 한 사이클 실측·복구 리허설·성능 검증 → v1.0.0
```

원문 수집은 Phase 3 이후에도 중단하지 않습니다. 새 문구가 들어오면 `FAILED` 또는 미확정
상태로 드러나고, 가공 픽스처와 규칙을 추가한 뒤 안전하게 재파싱하는 것이 정상 운영
루프입니다.

## Gate C0 — “충분히 수집됐다”의 판정 기준

고정된 일수만으로 통과시키지 않습니다. 아래 세 묶음을 모두 만족해야 합니다.

### C0-1. 개인정보·전송 안전성

- [ ] 일반 카카오 개인/단체 대화가 로컬 pending와 서버 `/raw`를 늘리지 않음
- [ ] 미등록 발신자의 개인 SMS와 미등록 일반 앱 알림이 저장되지 않음
- [ ] 등록한 금융 앱에서 의도하지 않은 민감 알림이 들어오지 않았는지 `/raw`로 점검
- [ ] 정상 네트워크에서는 모든 가족 폰의 pending가 다시 0이 됨
- [ ] rejected가 0이거나, 각 항목의 원인을 앱 안에서 확인해 처리 방침을 정함
- [ ] 기내모드 캡처 → 연결 복구, 서버 중단 → 재기동, 폰 재부팅 뒤 업로드를 실기기로 확인
- [ ] WebView가 로그인 없이 열리되 DEVICE 세션은 본인 데이터만 보여줌

하나라도 사적 알림이 저장되면 Phase 3 진입보다 수집 경계 수정이 먼저입니다. 잘못 수집된
`RawMessage`는 임의로 삭제하지 않고 사용자와 별도 처리 방침을 결정합니다.

### C0-2. 문구·출처 커버리지

아래 수치는 **최소 목표**이며, 카드 사용 패턴상 해당하지 않는 유형은 “해당 없음”으로
명시합니다. 단순히 건수만 채우려고 불필요한 결제를 만들 필요는 없습니다.

| 구분 | 최소 목표 | 이유 |
|---|---|---|
| 사용 중인 카드 | 카드 한 장마다 승인 알림 1건 이상 | 실제 카드 표기와 마스킹 형태 확인 |
| 카드사×출처 조합 | 조합마다 승인 3건 이상, 가능하면 서로 다른 2일 | 일회성 문구를 일반 규칙으로 오인하지 않기 |
| 복수 출처 동시 알림 | 실제로 함께 오는 조합마다 같은 결제 묶음 3개 권장 | 시간차·가맹점 표기 차이와 안전한 대사 기준 관찰 |
| 서로 다른 연속 결제 | 같은 금액 또는 같은 가맹점의 별도 결제 반례 1쌍 이상 권장 | 과도한 자동 병합 방지 |
| 전액 취소 | 프로젝트 전체 최소 1쌍 | 원거래 링크와 `netAmount` 검증 |
| 부분 취소 | 실제 사용하는 카드에서 가능할 때 1쌍 | 누적 취소와 잔여액 검증 |
| 할부 | 실제 사용하는 경우 1건 이상 | 할부 개월 추출 |
| 해외·외화 | 실제 사용하는 경우 승인과 후속 문구 | 외화/원화 확정액 차이 관찰 |
| 비거래 금융 알림 | 등록 앱별로 자연히 도착한 종류를 보존 | `IGNORED` 규칙의 근거 |

건수보다 **서로 다른 문구 구조**가 중요합니다. 같은 형식 100건보다 승인·취소·마스킹·복수
출처 반례가 각각 있는 편이 파서 설계에 더 유용합니다.

커버리지 표에는 실제 금액·가맹점·카드번호·사람 이름을 적지 않습니다. 다음처럼 식별 불가능한
상태만 기록합니다.

```text
issuer-A / CARD_APP / approval-format-01  7건
issuer-A / PAYMENT_APP / approval-format-02  5건
multi-source-pair-01  3묶음
full-cancel-format-01  1쌍
```

### C0-3. 운영 기준선

- [ ] 실제 서명 키를 암호화해 두 곳 이상 백업
- [ ] 서명 릴리스 APK의 설치와 덮어쓰기 업데이트 검증
- [ ] `familycard_live`의 보존 백업을 만들고 격리된 DB에서 읽을 수 있음을 확인
- [ ] 백업·작업물·이슈·PR에 실제 원문이나 장기 기기 토큰이 없음을 확인
- [ ] 현재 앱·서버 버전과 RawMessage 총건수·출처별 건수만 운영 메모에 기록
- [ ] [Phase 2 체크리스트](phase-2.md)의 필수 완료 항목을 마감

전체 자동 백업과 복구 훈련은 Phase 6~7에서 완성하지만, Phase 3의 첫 스키마 migration
전에는 **일회성 보존 백업과 격리 복원 확인**이 반드시 필요합니다.

Gate C0가 통과되면 `CHANGELOG`를 `0.2.0` 섹션으로 끊고 PR·CI·태그 절차로 `v0.2.0`을
발행합니다. 그 뒤에만 Phase 3 구현을 시작합니다.

## 실제 원문을 안전하게 분석하는 방법

### 원문이 머무는 곳

- 실제 제목·본문·카드 표기·거래 시각은 운영 DB와 접근 제어된 `/raw` 안에서만 봅니다.
- 원문을 로컬 텍스트 파일, 스프레드시트, 메신저, GitHub 이슈, PR 본문에 복사하지 않습니다.
- 스크린샷도 금융정보 복제본이므로 분석 전달 수단으로 쓰지 않습니다.
- 서버 로그에는 지금처럼 device ID와 건수·상태만 남깁니다.

### 두 종류의 정답셋

Phase 3 시작 시 실제 DB 안에서만 다음 정답 관계를 표시할 수 있는 검토 방식을 설계합니다.

1. **파서 정답셋**
   - 이 원문이 거래인지 무시 대상인지
   - 카드사·승인/취소·카드·시각·금액·가맹점 필드의 기대값
2. **대사 정답셋**
   - 서로 다른 RawMessage가 같은 실제 결제를 가리키는 양성 묶음
   - 비슷해 보여도 서로 다른 결제인 음성 반례

정답값 자체도 금융 데이터이므로 DB 밖으로 내보내지 않습니다. 코드 테스트에는 아래 절차로
만든 **가공 픽스처**만 사용합니다.

### 가공 픽스처 변환 체크

- 이름·가맹점·금액·카드번호·승인번호·외화금액을 전부 가짜 값으로 교체
- 패키지·채널 식별이 규칙에 필요하면 개인화되지 않은 공식 식별자만 유지
- 구두점·공백 수·줄바꿈·괄호·마스킹 문자 위치는 원문 구조와 동일하게 유지
- 실제 값의 일부를 “조금만” 남기는 방식은 금지
- 커밋 전 diff를 다시 읽어 실제 거래 단서가 없는지 확인

실제 DB 정답셋과 가공 테스트 픽스처가 같은 구조를 대표하는지는 사람이 `/raw`에서 대조하되,
둘을 자동으로 내보내거나 연결하는 파일은 만들지 않습니다.

## Phase 3 실행 순서 — 파서·카드 매칭

Phase 3은 한 번의 큰 PR로 만들지 않습니다. 다음 작업 패키지가 기본 순서입니다.

### P3-A. 원문 인벤토리와 설계 결정

산출물:

- 실제 값 없는 카드사×출처×문구형식 커버리지 표
- 파서·대사 양성/음성 정답셋을 운영 DB 안에서 표시하는 방식
- 복수 출처 의미 거래 모델 ADR
- 재파싱과 수동 편집 보존 전략 ADR 또는 기존 설계 보강

결정할 항목:

- 한 `Transaction`에 여러 `RawMessage` 근거를 연결하는 관계
  - 우선 검토안은 의미 거래와 원문 근거를 분리하는 연결 테이블
  - canonical/duplicate 링크 방식과 비교한 뒤 실제 데이터로 ADR에서 확정
- 자동 대사의 카드·금액·시각·가맹점 점수와 확정 임계값
- 애매한 후보의 검토 상태와 사람이 병합·분리하는 UI
- 대표 원문 선택 기준. 출처 우선순위는 대표 표시용일 뿐 원문 삭제 기준이 아님
- 운영 `ParserRule`을 DB에서만 관리할지, 복구 가능한 가공 기본 규칙을 버전 관리할지
- 사용자 편집 가능한 정규식의 컴파일 오류·과도한 역추적 방지 정책

실제 시간차와 가맹점 표기 차이를 보기 전에는 “3분 이내면 같은 결제” 같은 상수를 정하지
않습니다.

### P3-B. 보존형 스키마와 migration

구현 원칙:

- `RawMessage` 행은 한 건도 삭제·재작성하지 않음
- 현재 `Transaction.rawMessageId` 1:1 관계를 새 근거 관계로 안전하게 backfill
- 의미 거래, 원문 근거, 사람이 확인한 병합/분리, 수동 편집의 소유권을 구분
- `MANUAL`·`STATEMENT`처럼 Android 기기에서 오지 않은 원문의 소유자/provenance 모델 결정;
  현재 필수 `RawMessage.deviceId`를 채우려고 가짜 Device를 만들지 않음
- 재파싱 결과가 바뀌어도 이전 거래를 즉시 잃지 않을 감사 정보 검토
- SELF/FAMILY 조회가 모두 `visibleMemberIds(session)`를 거치도록 인덱스·쿼리 설계

검증 순서:

1. 운영 백업의 격리 복원본에 migration 적용
2. migration 전후 RawMessage 총건수와 ID 집합 동일 확인
3. 기존 가공 데이터와 실제 원문이 모두 보존됐는지 건수·해시로 확인
4. rollback은 데이터 삭제가 아니라 백업 복원 절차로 준비
5. CI의 schema↔migration diff와 테스트 통과 후 PR 병합

### P3-C. 순수 파서 코어

DB 쓰기 전에 `RawMessage` 입력을 명시적 결과 타입으로 바꾸는 순수 모듈부터 만듭니다.

```text
PARSED_CANDIDATE | IGNORED | NO_RULE | INVALID_FIELDS
```

필수 범위:

- `ParserRule` priority와 첫 매치 규칙
- `money`, `installment`, `datetime_md`, `text`, `card_token`, `const` 변환기
- `receivedAt` 기준 KST 연도 복원
- 원 단위 정수와 해외 통화 필드 검증
- 정규식·`fieldMap` 런타임 검증과 안전한 실패
- 원문이나 추출 필드를 로그에 남기지 않는 오류 경계

운영 규칙은 인증된 관리 UI의 `ParserRule` 데이터로 다루고, 코드 테스트에는 같은 구조의
가공 규칙과 픽스처만 둡니다. 기본 규칙을 배포·복구하는 방식은 P3-A에서 결정합니다.
카드사/출처별 규칙 지원은 한 묶음씩 별도 PR로 검증하며, 각 PR은 해당 문구형식의 가공 승인,
취소, 할부, 해외, 마스킹, 무시 대상 픽스처 중 실제로 관찰된 범위를 포함합니다.

### P3-D. 카드 등록과 카드 매칭

- 사용자가 카드사·상품 별칭·실물 뒷 4자리·결제일을 안전하게 등록·비활성화
- 후보군은 반드시 원문 소유자의 `memberId`와 issuer로 제한
- `CardAlias` → 정확 일치 → 마스킹 단일 후보 → 별칭 단일 후보 순
- 2개 이상 후보나 식별자 없음은 `NEEDS_CARD`; 추측 금지
- 사람이 지정하면 alias를 학습하되 다른 구성원의 카드에는 영향 없음

권한 회귀 테스트는 기능과 같은 PR에 넣습니다.

### P3-E. 복수 출처 의미 대사

파싱된 후보를 다음 순서로 보수적으로 묶습니다.

1. 같은 구성원인지
2. 같은 카드 또는 양립 가능한 카드 표기인지
3. 승인/취소 종류와 금액이 같은지
4. 실제 데이터에서 정한 시각 허용 범위인지
5. 정규화한 가맹점이 충분히 가까운지
6. 최고 후보가 임계값 이상이고 2위와 충분한 격차가 있는지

확신이 부족하면 **합치지 않고 검토 대상으로 둡니다.** 정답셋에서 다음 두 조건을 모두
검증해야 합니다.

- 같은 결제의 카드사 앱+결제 앱 원문은 전부 남고 집계는 한 번
- 같은 금액·가맹점의 연속된 실제 별도 결제는 두 거래

사람이 잘못된 자동 묶음을 분리하고 애매한 묶음을 확정할 수 있는 역연산도 설계합니다.

### P3-F. 취소와 `netAmount`

복수 출처 승인을 한 의미 거래로 만든 뒤 취소를 적용합니다. 취소 알림 자체도 여러 출처에서
올 수 있으므로 **취소 원문의 의미 중복 대사가 먼저**입니다.

- 전액·부분·반복 부분취소
- 잔여액 초과 후보 실격
- 60일 후보 범위는 실제 데이터로 재검토
- 최고점/2위 격차 미달은 사람 확인
- 고아 취소 표시와 수동 원거래 연결
- 하나의 DB 트랜잭션으로 링크와 누적액 반영
- 재파싱 시 관련 `canceledAmount`를 0에서 전체 재구축해 이중 차감 방지

모든 월간 사용금액·실적 쿼리는 `amount`가 아니라 `netAmount`를 사용합니다.

### P3-G. 미확정 큐와 재파싱

- `FAILED`, `NEEDS_CARD`, 대사 애매, 취소 원거래 미확정을 이유별로 분리 표시
- 규칙 저장 전 전체 대상에 dry-run
- `wouldFix`, `wouldChange`, `wouldBreak`, `skippedManual` 제공
- `wouldBreak > 0`이면 명시적 경고와 적용 차단/재확인
- 파싱 실패만으로 기존 거래를 삭제하지 않음
- `isManuallyEdited`와 사람이 확인한 병합/분리를 자동 재파싱이 덮지 않음
- 같은 범위를 두 번 재파싱해도 거래 수·취소액·집계가 동일한 멱등성 테스트

### P3-H. 카드별 월간 사용 화면

- 카드별 승인 거래의 `netAmount` 합계
- KST 월 경계를 UTC로 변환해 조회
- 미확정 카드 금액은 별도 행, 특정 카드 실적에는 포함하지 않음
- 거래 상세에서 근거 원문 출처 수와 파싱/수동 상태를 확인
- 앱 DEVICE 세션은 본인만, 웹 ADMIN FAMILY 세션만 허용된 가족 범위 조회

### Phase 3 완료 게이트

- [ ] 검토한 모든 문구형식에 가공 회귀 픽스처 또는 의도적 `IGNORED` 근거가 있음
- [ ] 거래성 검토 원문의 95% 이상이 자동 처리되고 나머지는 모두 이유가 보이는 미확정 상태
- [ ] 대사 정답셋의 알려진 오병합·누락 병합이 0건
- [ ] 다른 구성원 카드로 붙은 거래가 0건
- [ ] 재파싱 2회 뒤 거래 수·근거 관계·`canceledAmount`·월 합계가 동일
- [ ] RawMessage 총건수와 ID 집합이 Phase 3 전후 동일
- [ ] 카드별 월간 합계를 접근 제어된 원문/카드사 화면과 표본 대조
- [ ] 모든 조회 scope 테스트와 전체 CI 통과

95%는 잘못된 자동 확정을 허용한다는 뜻이 아닙니다. **틀리게 자동 처리하는 것보다 명확한
미확정으로 남기는 것이 우선**이며, 알려진 오병합과 오카드 매칭의 허용치는 0건입니다.

## Phase 4~7 실행 게이트

### Phase 4 — 실적 엔진 (`v0.4.0`)

1. 공식 카드 약관을 기준으로 카드별 구간·제외·사이클·취소 정책 입력
2. 순수 실적 엔진을 `netAmount`와 KST 경계로 구현
3. 제외 사유와 미확정 금액을 UI에서 설명
4. 모든 실적 숫자에 **추정치** 표시
5. 우선 카드 1장을 한 사이클 동안 카드사 앱 수치와 대조해 규칙 튜닝

완료 게이트는 경계/취소/제외 유닛 테스트, 추정치 표기, 한 카드 실측 대조입니다. 약관 조사와
프리셋 준비는 Phase 3 후반에 할 수 있지만, 거래 모델이 안정되기 전 집계 코드를 만들지
않습니다.

### Phase 5 — 관리자 가족 대시보드 (`v0.5.0`)

1. 가족×카드 사용액·실적 매트릭스
2. 구성원 드릴다운과 미확정/수집기 무응답 현황
3. 카테고리·예산·분석
4. MEMBER/ADMIN/DEVICE 진입 경로별 공격 회귀 테스트

완료 게이트의 핵심은 화면 수가 아니라 **타인 데이터 누출 0건**입니다. 모든 새 조회는
`visibleMemberIds(session)`를 경유하고, ADMIN 폰 앱은 계속 SELF여야 합니다.

### Phase 6 — 보정·운영 (`v0.6.0`)

1. 카드사 엑셀/CSV를 `STATEMENT` 원문으로 보존하며 import
2. 알림 거래와 명세서의 누락·초과·금액 불일치 대사
3. 수집기 `lastSeenAt` 무응답 경고와 실적 미달/취소 소급 알림
4. 일·주·월 백업 보존, 디스크 감시, 운영 업데이트 절차
5. 격리 환경 복구 절차 문서화와 최소 1회 복원 시험

Phase 3 전의 백업은 migration 안전망이고, Phase 6의 백업은 장기 자동 운영 체계입니다.

P3-B에서 정한 비기기 원문 provenance 모델을 명세서에 적용합니다. 구성원·업로드 파일·행의
관계를 보존하고, XLSX 바이너리를 `RawMessage.body`에 넣을지 파일 메타데이터와 정규화한 행을
분리할지는 Phase 6 ADR에서 확정합니다. 실제 명세서 파일은 Git에 넣지 않습니다.

### Phase 7 — 실사용 검증 (`v1.0.0`)

1. 가족 전원과 전 카드가 최소 한 실적 사이클 이상 사용
2. 전 카드의 FamilyCard 추정치와 카드사 공식 수치 대조
3. 새 알림 형식·누락·미확정 추이를 반영
4. 실제 운영 백업 복구 리허설
5. 수개월 데이터에서 성능 측정과 인덱스 튜닝
6. 사용자·관리자 가이드와 미해결 이슈·릴리스 노트 정리

`v1.0.0`은 기능이 존재한다는 뜻이 아니라 **숫자의 한계가 설명되고 실사용으로 검증됐다**는
뜻입니다.

## 지금부터 사용자가 할 일

- 앱을 지우지 말고 자연스럽게 원문을 계속 수집
- 가끔 설정에서 pending 0, rejected 0인지 확인
- 대시보드 **수집 원문 보기**에서 의도한 금융 알림만 들어오는지 확인
- 같은 결제를 여러 앱이 알리면 둘 다 보이는 것이 현재는 정상
- 취소·할부·해외를 실제로 이용한 날에는 해당 유형이 도착했는지만 앱 안에서 확인
- 실제 원문을 스크린샷·메신저·GitHub로 전달하지 않기

“충분히 모인 것 같다”고 판단되면 개발자는 먼저 **읽기 전용 건수·출처·형식 인벤토리**만
작성해 Gate C0 충족 여부를 보고합니다. 부족한 유형이 있으면 파서를 시작하지 않고 무엇이
더 필요한지만 안내합니다.
