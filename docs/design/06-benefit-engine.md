# 06 — 실적 엔진

## 이 프로젝트의 목표

"이번 달 얼마 썼나"는 카드사 앱에서도 볼 수 있습니다. 이 시스템이 존재하는 이유는 **가족이 가진 카드 전부의 실적 달성 현황을 한 화면에서 보는 것**입니다.

전월실적은 카드 혜택의 전제 조건입니다. 30만원을 채웠으면 할인이 나오고, 29만원이면 안 나옵니다. 그런데 카드가 여러 장이면 어느 게 모자란지 추적하기 어렵고, 그래서 실적을 못 채워 혜택을 놓치는 일이 반복됩니다.

---

## 먼저: 이 값은 추정치입니다

**표시되는 실적은 카드사의 공식 수치가 아닙니다.** 알림 파싱 방식의 구조적 한계 때문에 완전히 일치할 수 없습니다.

| 오차 원인 | 영향 |
|---|---|
| 할부 변경 (일시불 → 할부 전환) | 실적 산정 방식이 달라짐 |
| 해외 결제 환율 확정 | 승인액과 청구액이 다름 |
| 알림 누락 (최소 금액 임계값, 권한 꺼짐) | 실적이 실제보다 적게 나옴 |
| 제외 항목 기준 | 카드사 약관에 다 적혀 있지 않음 |
| 미확정 카드 건 | 실적에서 제외됨 |

**UI의 모든 실적 표시에 "추정치"를 명시합니다.** → [불변 규칙 6](../../AGENTS.md)

사용자가 이 숫자를 공식 수치로 오인하면 실제로 손해를 봅니다. "달성했다"고 믿고 안 썼는데 미달이었다면 혜택을 놓치는 것이고, 이건 시스템이 아예 없는 것보다 나쁩니다.

Phase 6의 **명세서 대사**로 오차를 줄입니다. 그전까지는 **실제 카드사 앱 수치와 대조해가며 제외 규칙을 튜닝**하는 것이 유일한 검증 수단입니다.

## `CardBenefitRule`

카드 1장당 최대 1개의 규칙을 둡니다.

```ts
{
  cardId: "...",

  // 실적 산정 기간
  periodType: "PREV_CALENDAR_MONTH" | "STATEMENT_CYCLE",

  // 실적 구간과 혜택
  tiers: [
    { threshold: 300000,  benefitDesc: "주요 가맹점 5% 할인", monthlyCap: 10000 },
    { threshold: 700000,  benefitDesc: "주요 가맹점 7% 할인", monthlyCap: 20000 },
    { threshold: 1000000, benefitDesc: "전 가맹점 5% 할인",   monthlyCap: 30000 },
  ],

  // 실적 제외 항목
  exclusions: ["TAX", "INSURANCE", "GIFT_CARD", "PREPAID", "APT_FEE", "TRANSIT", "TUITION"],

  // 건별 최소 인정 금액 (0이면 제한 없음)
  minPerTxAmount: 10000,

  // 취소를 어느 사이클에서 뺄지
  cancellationPolicy: "DEDUCT_FROM_ORIGINAL",
}
```

`tiers`는 `threshold` 오름차순. 현재 실적으로 달성한 **가장 높은 구간**이 적용됩니다.

---

## 산정 기간

### `PREV_CALENDAR_MONTH`

전월 1일 00:00 ~ 말일 23:59:59 (**KST**). 가장 흔한 방식입니다.

```
2026년 8월의 혜택 판정 → 2026-07-01 00:00 ~ 2026-07-31 23:59:59 (KST)
```

### `STATEMENT_CYCLE`

결제일 기준 사이클. `Card.statementDay`를 씁니다.

```
statementDay = 14 이면
  → 전월 15일 ~ 당월 14일
```

### 시간대 함정

`Transaction.approvedAt`은 DB에 **UTC**로 저장됩니다. 사이클 경계는 **KST** 기준입니다.

UTC 그대로 월 경계와 비교하면 **매월 초·말에 9시간만큼 어긋납니다.** 7월 31일 저녁 10시(KST) 결제는 UTC로 7월 31일 13시라 우연히 맞지만, 8월 1일 새벽 2시(KST) 결제는 UTC로 7월 31일 17시라 **7월 실적에 잘못 들어갑니다.**

```ts
// ✅ 사이클 경계를 KST 로 만들고 UTC 로 변환해서 비교
const startKst = zonedTimeToUtc(startOfMonth(prevMonth), 'Asia/Seoul');
const endKst   = zonedTimeToUtc(endOfMonth(prevMonth),   'Asia/Seoul');

// ❌ UTC 기준 월 경계를 그대로 사용
```

## 제외 항목

카드사가 실적으로 인정하지 않는 결제들입니다. **이 판정의 정확도가 실적 추정치의 품질을 결정합니다.**

### 거의 모든 카드에서 제외

| 코드 | 대상 |
|---|---|
| `TAX` | 국세(소득세·부가세 등), 지방세(재산세·자동차세·주민세 등) |
| `INSURANCE` | 4대 보험 — 건강보험, 국민연금, 고용보험, 산재보험 |
| `GIFT_CARD` | 상품권 구매 (백화점·모바일 상품권·기프티콘 포함) |
| `PREPAID` | 선불 충전 (교통카드 충전, 각종 페이 충전) |
| `APT_FEE` | 아파트 관리비 |
| `TRANSIT` | 후불 교통 |
| `TUITION` | 대학 등록금 |

### 카드마다 갈리는 항목 — **토글로 제공**

| 코드 | 대상 |
|---|---|
| `UTILITY_GAS` | 도시가스 |
| `UTILITY_ELEC` | 전기요금 |
| `UTILITY_WATER` | 수도요금 |
| `TELECOM` | 이동통신 요금 |
| `INTERNET` | 인터넷·유선방송 |

이 다섯은 카드에 따라 실적으로 인정하기도, 안 하기도 합니다. 하드코딩하면 절반은 틀립니다. **카드별 체크박스**로 사용자가 약관을 보고 설정하게 합니다.

### 판정 방법

가맹점명과 카테고리를 함께 봅니다.

```
1. Transaction.categoryId 가 제외 카테고리에 속하는가
2. merchantName 이 제외 패턴에 걸리는가
   (예: /국세|지방세|위택스|홈택스|건강보험|국민연금/)
3. 둘 중 하나라도 해당하면 excludeReason 기록
```

`excludeReason`은 **거래에 저장**합니다. UI에서 "이 건은 국세라 실적에서 빠졌습니다"라고 설명할 수 있어야 하기 때문입니다. 실적 계산이 블랙박스면 숫자가 안 맞을 때 사용자가 원인을 찾을 방법이 없습니다.

### 건별 최소 금액

`minPerTxAmount`가 설정된 카드는 그 미만 결제를 실적에서 뺍니다.

```
minPerTxAmount = 10000 이면
  9,900원 결제 → excludeReason = "MIN_AMOUNT"
```

## 산정 절차

```
입력: cardId, 기준 사이클

1. 사이클 경계 계산 (KST 기준, periodType 에 따라)

2. 대상 거래 조회
   - cardId 일치
   - approvedAt 이 사이클 내
   - txType = APPROVAL
   - ★ cardId 가 null 인 미확정 건은 자동으로 제외됨

3. 각 거래에 대해 제외 판정
   - 제외 항목 해당 → excludeReason 기록, 실적에서 뺌
   - minPerTxAmount 미만 → 제외
   - 나머지 → 실적에 포함

4. 취소 반영 (cancellationPolicy 에 따라)
   - DEDUCT_FROM_ORIGINAL: 이 사이클 거래들의 canceledAmount 를 뺌
   - DEDUCT_FROM_CANCEL_PERIOD: 이 사이클에 발생한 취소액을 뺌
     (원거래가 이전 사이클이어도 여기서 차감)

5. 실적액 = SUM(netAmount of 포함 거래)

6. tiers 에서 달성 구간 판정
   - 달성한 가장 높은 threshold
   - 다음 구간까지 남은 금액
```

**2번의 ★ 표시**: 미확정 건(`cardId = null`)은 어느 카드 조회에도 걸리지 않으므로 자연스럽게 제외됩니다. 이건 의도된 동작입니다. → [04-card-matching](04-card-matching.md)

## 화면에 보여줄 것

### 카드별 실적 카드

```
┌──────────────────────────────────────────┐
│ 신한 딥드림 (1234)          [추정치]      │
│                                          │
│ ████████████████░░░░░░  245,000 / 300,000│
│                                          │
│ 55,000원 더 쓰면 5% 할인 구간 달성        │
│                                          │
│ 이번 사이클: 7/1 ~ 7/31                   │
│ 제외된 건 3건 (52,000원) ▸                │
└──────────────────────────────────────────┘
```

핵심은 **"N원 더 쓰면 달성"** 입니다. 실적 숫자 자체보다 행동으로 이어지는 정보입니다.

`제외된 건 3건 ▸`을 펼치면 각 거래와 제외 사유가 나옵니다. 이게 있어야 사용자가 숫자를 신뢰하거나, 틀렸을 때 규칙을 고칠 수 있습니다.

### 미확정 경고

```
⚠️ 카드 미확정 2건(38,000원)이 실적에 반영되지 않았습니다  [지정하러 가기]
```

### 카드 추천 (Phase 4 후반)

이번 달 실적 여유가 있는 카드를 안내합니다.

```
💡 이번 달은 롯데 로카를 쓰세요 — 12만원 더 쓰면 구간 달성
   (신한 딥드림은 이미 달성, 더 써도 추가 혜택 없음)
```

`monthlyCap`(혜택 한도)을 이미 채운 카드는 더 써도 이득이 없으므로 추천에서 뺍니다.

## 규칙 편집 UI

실적 규칙은 **사용자가 카드사 약관을 보고 직접 입력**합니다. 자동으로 알아낼 방법이 없습니다.

- 구간(`tiers`) 추가·삭제, 임계값과 혜택 설명 입력
- 제외 항목 체크박스 — 공통 항목은 기본 체크, 카드별 갈리는 항목은 사용자가 선택
- 산정 기간 방식 선택
- 건별 최소 금액
- 취소 차감 정책

**입력 부담을 줄이는 장치**로, 흔한 카드 유형의 프리셋을 제공합니다(예: "전월실적 30/70/100만원 3구간, 공과금 제외"). 사용자는 프리셋을 고르고 다듬기만 하면 됩니다.

## 검증

이 모듈의 진짜 검증은 유닛 테스트가 아니라 **실제 카드사 앱의 전월실적 수치와 대조**하는 것입니다.

```
1. 카드사 앱에서 전월실적 확인 (예: 신한 딥드림 284,300원)
2. FamilyCard 의 추정치 확인 (예: 291,000원)
3. 차이 6,700원의 원인 추적
   → 제외된 건 목록을 열어 카드사가 뺐는데 우리는 안 뺀 항목을 찾음
   → 예: 통신비 6,700원 → UTILITY/TELECOM 토글을 켬
4. 다시 대조
```

이 튜닝 과정을 관리자 가이드에 절차로 적어둡니다. 처음 한 달은 오차가 나는 게 정상입니다.

### 유닛 테스트

```
✅ 구간 경계값 (정확히 300,000원 → 달성)
✅ 구간 경계 -1원 (299,999원 → 미달)
✅ 제외 항목이 실적에 안 잡힘 (국세, 상품권)
✅ minPerTxAmount 미만 제외
✅ 미확정 건(cardId=null)이 어느 카드 실적에도 안 들어감
✅ 전액 취소 후 실적 감소
✅ 부분 취소 후 실적 감소
✅ 실적 달성 후 취소 → 미달로 전환
✅ DEDUCT_FROM_ORIGINAL vs DEDUCT_FROM_CANCEL_PERIOD 차이
✅ KST 자정 경계 — 8/1 00:30(KST) 결제가 7월 실적에 안 들어감 ★
✅ 월말/월초 사이클 경계 (31일, 2월, 윤년)
✅ STATEMENT_CYCLE 사이클 계산
```

★ 표시한 시간대 테스트는 반드시 넣으세요. UTC/KST 혼동은 조용히 틀리고, 매월 며칠만 증상이 나타나 발견이 늦습니다.
