# 05 — 취소 처리

## 왜 별도 문서가 필요한가

취소를 제대로 반영하지 않으면 **이 프로젝트의 존재 이유가 무너집니다.**

30만원 실적 조건인 카드에서 29만원을 쓰고 5만원짜리를 반품했다면, 실제 실적은 24만원입니다. 취소를 무시하면 시스템은 "29만원 달성 임박"이라고 표시하고, 사용자는 1만원만 더 쓰면 된다고 믿습니다. 그러면 혜택을 놓칩니다.

취소는 예외 케이스가 아니라 **일상적으로 발생하는 정상 흐름**입니다.

---

## 취소의 세 가지 형태

| 형태 | 상황 | 처리 |
|---|---|---|
| **전액 취소** | 반품, 결제 오류 | 원거래를 통째로 무효화 |
| **부분 취소** | 여러 품목 중 일부 반품 | 금액 일부만 차감. **여러 번 올 수 있음** |
| **고아 취소** | 원거래를 못 찾음 | 앱 설치 전 결제의 취소 등 |

부분 취소가 여러 번 오는 경우가 설계의 까다로운 지점입니다. 10만원 결제에서 3만원, 2만원을 따로 반품하면 취소 알림이 두 건 옵니다.

---

## 데이터 모델 선택

취소를 어떻게 저장할지에 두 가지 방식이 있었습니다.

**방식 A — 취소를 음수 거래로 저장**
```
Transaction { amount: +100000, ... }   원거래
Transaction { amount:  -30000, ... }   취소 1
Transaction { amount:  -20000, ... }   취소 2
집계 = SUM(amount)
```

**방식 B — 원거래에 취소액을 누적** ← **채택**
```
Transaction { amount: 100000, canceledAmount: 50000, ... }   원거래
Transaction { txType: CANCELLATION, canceledTxId: <원거래>, ... }  취소 1, 2
집계 = SUM(amount - canceledAmount)
```

방식 B를 고른 이유:

1. **실적 사이클 귀속이 자연스럽다.** 취소를 어느 달 실적에서 뺄지는 원거래가 언제 발생했느냐에 달려 있는데(아래 참고), 방식 A에서는 취소 행이 자기 시점에 매달려 있어 매번 원거래를 역추적해야 합니다
2. **원거래 하나를 보면 현재 상태를 알 수 있다.** `netAmount = amount - canceledAmount`
3. **부분 취소가 여러 번 와도 누적이 정확하다**

방식 B의 대가는 취소 알림 처리가 단순 삽입이 아니라 **원거래 탐색 + 갱신**이라는 점입니다. 그 복잡도를 감수할 가치가 있다고 판단했습니다.

---

## 원거래 매칭

취소 알림이 도착하면 어느 결제의 취소인지 찾아야 합니다.

### 후보 조회

```ts
const candidates = await prisma.transaction.findMany({
  where: {
    cardId,                                    // 같은 카드
    txType: 'APPROVAL',
    approvedAt: {
      lte: cancelTx.approvedAt,                // 취소 시점 이전
      gte: subDays(cancelTx.approvedAt, CANCELLATION_LOOKBACK_DAYS),  // 기본 60일
    },
    // 이미 전액 취소된 건은 제외
    // (amount > canceledAmount 인 것만)
  },
  orderBy: { approvedAt: 'desc' },
});
```

`Transaction(cardId, amount, approvedAt)` 복합 인덱스가 이 쿼리를 위한 것입니다.

### 점수 매기기

후보 중 최적을 고릅니다. 단일 기준으로는 애매한 경우가 많아 가중치를 씁니다.

| 조건 | 점수 |
|---|---|
| 가맹점명 완전 일치 | +50 |
| 가맹점명 부분 일치 | +25 |
| 금액이 정확히 일치 (전액 취소) | +40 |
| 취소액 ≤ 잔여액 (부분 취소 가능) | +20 |
| 취소액 > 잔여액 | **실격** |
| 최근일수록 | +최대 10 (선형 감쇠) |

**실격 조건이 중요합니다.** 잔여액보다 큰 금액은 그 거래의 취소일 수 없습니다. 이걸 거르지 않으면 `canceledAmount`가 `amount`를 넘어 `netAmount`가 음수가 됩니다.

### 판정

```
최고점 후보의 점수 >= 임계값(60)  그리고
2위와의 점수 차 >= 15            →  확정

그 외                             →  미확정 큐 (사람이 지정)
```

2위와의 격차를 요구하는 이유: 같은 가맹점에서 같은 금액을 두 번 결제한 경우(정기구독 등) 어느 쪽 취소인지 알 수 없습니다. 이때 아무거나 고르면 실적 귀속 달이 틀릴 수 있습니다.

실무적으로는 두 후보 중 어느 쪽을 골라도 금액 합계는 같으므로, 미확정 큐에서 "최근 것으로 처리" 기본 선택지를 제공해 클릭 한 번에 끝나게 합니다.

---

## 반영

```ts
await prisma.$transaction([
  // 1. 원거래에 취소액 누적
  prisma.transaction.update({
    where: { id: originalTx.id },
    data: { canceledAmount: { increment: cancelAmount } },
  }),
  // 2. 취소 거래에 링크 저장
  prisma.transaction.update({
    where: { id: cancelTx.id },
    data: { canceledTxId: originalTx.id },
  }),
]);
```

**반드시 하나의 DB 트랜잭션으로.** 중간에 실패해서 원거래만 갱신되고 링크가 안 생기면, 재파싱 시 같은 취소가 다시 누적되어 이중 차감됩니다.

### 재파싱 시 이중 차감 방지

재파싱은 이 시스템의 핵심 기능이라, 취소가 여러 번 반영되지 않도록 해야 합니다.

```
재파싱 대상 원문이 취소 거래인 경우:
  1. 기존 Transaction 에 canceledTxId 가 있으면
     → 그 원거래의 canceledAmount 에서 먼저 차감 (되돌리기)
  2. 새로 매칭해서 다시 누적
```

또는 더 안전하게: **재파싱 시 관련 원거래들의 `canceledAmount`를 0으로 초기화한 뒤, 취소 거래 전체를 재적용**합니다. 가족 규모의 데이터량(월 수백 건)에서는 이 방식의 비용이 문제 되지 않고, 실수할 여지가 훨씬 적습니다.

---

## 고아 취소

원거래를 못 찾는 경우입니다.

- 앱 설치 **전에** 한 결제를 설치 **후에** 취소
- 원거래 알림이 유실됨 (알림 설정이 꺼져 있었거나 최소 금액 임계값에 걸림)
- 60일보다 오래된 결제의 취소

```
Transaction {
  txType: CANCELLATION,
  isOrphanCancellation: true,
  canceledTxId: null,
  amount: <취소액>,
}
```

**집계 처리**: 취소 시점이 속한 사이클에서 **음수로 차감**합니다. 원거래를 모르니 다른 선택지가 없습니다.

UI에는 "원거래 미확인"으로 표시합니다. 사용자가 보고 "아, 지난달 그거구나" 하고 판단할 수 있게, 금액·가맹점·시각을 함께 보여줍니다. 원한다면 수동으로 원거래를 지정할 수 있게 합니다.

---

## 실적에서 어느 달에 차감하는가

**여기가 카드사마다 갈리는 지점입니다.**

3월에 결제하고 4월에 취소했다면, 3월 실적에서 빼는 걸까요 4월에서 빼는 걸까요?

| 정책 | 동작 | 언제 쓰나 |
|---|---|---|
| `DEDUCT_FROM_ORIGINAL` **(기본값)** | 원거래가 속한 사이클에서 차감 | 대부분의 카드사 관행 |
| `DEDUCT_FROM_CANCEL_PERIOD` | 취소가 발생한 사이클에서 차감 | 실적 마감 후 취소를 당월로 넘기는 카드 |

`CardBenefitRule.cancellationPolicy`로 **카드별 설정**입니다. 기본값은 `DEDUCT_FROM_ORIGINAL`.

### 왜 기본값이 이것인가

카드사는 보통 "3월 이용금액"을 산정할 때 3월에 발생한 결제의 최종 상태를 봅니다. 4월에 취소되면 3월 실적이 소급해서 줄어듭니다. 그래서 3월 실적이 마감된 것처럼 보였다가 나중에 미달로 바뀌는 일이 실제로 생깁니다.

다만 카드사가 이미 혜택을 지급한 뒤라면 소급하지 않고 당월에서 빼는 곳도 있습니다. 약관을 읽어봐야 알 수 있고, 그마저 명시돼 있지 않은 경우가 많습니다.

**그래서 설정으로 뺐습니다.** 실제 카드사 수치와 대조해보고 안 맞으면 이 값을 바꿔보는 것이 튜닝 절차입니다. 관리자 가이드에 안내합니다.

### 소급 변경의 UI 처리

`DEDUCT_FROM_ORIGINAL`이면 지난달 실적이 나중에 바뀔 수 있습니다. 사용자가 놀라지 않도록:

- 지난 사이클 실적에 "취소 반영으로 변경됨" 표시
- 실적이 달성 → 미달로 떨어지면 눈에 띄게 (Phase 6에서 알림 대상)

## 테스트

```
✅ 전액 취소        → netAmount = 0
✅ 부분 취소 1회     → canceledAmount = 취소액
✅ 부분 취소 2회     → canceledAmount = 합계 (누적 정확)
✅ 취소액 > 잔여액   → 그 후보는 실격, 다른 후보 탐색
✅ 원거래 없음       → isOrphanCancellation = true
✅ 60일 초과         → 고아 취소로 처리
✅ 후보 2건 동점     → 미확정 큐
✅ 재파싱 2회        → canceledAmount 가 두 배 되지 않음 ★
✅ 실적 달성 후 취소 → 실적이 미달로 떨어짐
✅ DEDUCT_FROM_ORIGINAL      → 원거래 달 실적 감소
✅ DEDUCT_FROM_CANCEL_PERIOD → 취소 달 실적 감소
```

★ 표시한 재파싱 이중 차감은 실제로 놓치기 쉬운 버그입니다. 반드시 테스트로 고정하세요.
