# 00 — 아키텍처 개요

## 풀려는 문제

가족 구성원 각자가 여러 장의 카드를 쓰지만, 누가 어떤 카드로 이번 달 얼마를 썼는지, 그리고 **각 카드의 전월실적을 채웠는지**를 한눈에 보는 수단이 없습니다. 카드사 앱을 사람 수 × 카드사 수만큼 들락거려야 하고, 실적 미달로 혜택을 놓치는 일이 반복됩니다.

목표는 **카드사별이 아니라 카드 한 장 단위로** 월간 사용금액과 실적 달성 추정치를 보여주는 것입니다. 실적은 카드마다 별도로 쌓이기 때문에, 카드사 단위 집계는 의미가 없습니다.

## 데이터를 어떻게 얻는가

한국에서 카드 사용내역에 프로그램으로 접근하는 경로는 셋뿐이고, 각각 문턱이 다릅니다.

| 경로 | 가능 여부 | 판단 |
|---|---|---|
| 마이데이터 표준 API | ❌ | 금융위 허가받은 마이데이터 사업자만. 개인 불가 |
| CODEF (스크래핑 중개 API) | ✅ | 기술적으로 최선. 승인내역·청구내역·**실적조회** API가 모두 있음. 단 건당 과금 |
| 안드로이드 알림·SMS 파싱 | ✅ | 비용 0. 대신 정확도에 구조적 한계 |

**알림 파싱을 선택했습니다.** 가족 단위 사용이라 지속적인 과금이 부담스럽고, 정확도 한계는 명세서 대사(Phase 6)로 보완할 수 있다고 판단했습니다. 배경은 [ADR 0001](../adr/0001-collection-method.md).

## 왜 서버가 필요한가

카드 결제 알림은 **각자 본인 폰에만** 옵니다. 폰 하나에 설치된 앱은 그 사람 데이터만 볼 수 있으므로, 가족 N명의 데이터를 합치려면 합류 지점이 반드시 필요합니다. "안드로이드 앱 하나로 끝내기"는 요구사항과 양립하지 않습니다. → [ADR 0002](../adr/0002-server-required.md)

## 전체 구조

```
[가족 폰 N대 — 앱 하나]              [집 서버 / NAS]
┌────────────────────────┐         ┌────────────────────────────────┐
│  FamilyCard App (Kotlin)│        │  Docker Compose                │
│                         │        │  ┌──────────────────────────┐  │
│ ┌─ 백그라운드 (안 보임) ─┐│        │  │ Next.js (App Router)     │  │
│ │ NotificationListener  ││──POST──┼─▶│  /api/ingest             │  │
│ │ SmsReceiver           ││ raw text│ │  파서 · 카드매칭 · 실적   │  │
│ │ Room 큐 + WorkManager ││        │  │  scope 기반 조회 계층     │  │
│ └───────────────────────┘│        │  └───────────┬──────────────┘  │
│ ┌─ 화면 ────────────────┐│        │              │                 │
│ │ [대시보드] WebView ────┼┼──GET───┼─▶┌───────────▼──────────────┐  │
│ │   scope=SELF (본인만) ││        │  │ PostgreSQL               │  │
│ │ [설정] Compose        ││        │  └──────────────────────────┘  │
│ └───────────────────────┘│        └────────────────────────────────┘
└────────────────────────┘                      ▲ Tailscale
                                    관리자 PC 브라우저 → scope=FAMILY
```

가족이 설치하는 것은 **앱 하나**입니다. 그 안의 대시보드는 실제로는 서버가 그리는 화면(WebView)이라, UI를 고쳐도 APK를 다시 깔 필요가 없습니다. 큰 화면에서 보고 싶으면 PC 브라우저로 같은 주소에 접속합니다.

## 컴포넌트 경계

### 안드로이드 앱 — "캡처하고 전달만"

책임:
- 화이트리스트에 든 알림·SMS를 캡처
- 로컬 큐에 쌓고 서버로 업로드 (재시도 포함)
- WebView로 서버 화면 표시
- 권한 상태와 전송 로그를 보여주는 설정 화면

**책임이 아닌 것: 파싱, 집계, 실적 계산.** 앱은 텍스트를 옮기는 파이프일 뿐입니다.

### 서버 — "해석하고 계산하는 전부"

```
raw 수신  →  파싱  →  카드 매칭  →  취소 매칭  →  집계·실적  →  화면
/api/ingest  lib/parser  lib/cardmatch              lib/benefit   app/
```

각 단계는 실패할 수 있고, 실패한 건은 버리지 않고 **미확정 큐**로 보내 사람이 개입할 수 있게 합니다.

## 핵심 설계 결정 4가지

### 1. 수집기는 파싱하지 않는다

앱은 알림 원문을 **그대로** 서버에 보냅니다. 파싱은 전부 서버에서 합니다.

이유: 카드사 알림 문구는 예고 없이 바뀝니다. 파싱이 앱에 있으면 문구가 바뀔 때마다 APK를 다시 만들어 가족 전원에게 재설치를 부탁해야 합니다. 서버에 있으면 `docker compose up -d` 한 번이면 되고, 더 중요하게는 **이미 쌓인 과거 원문을 새 규칙으로 재파싱**할 수 있습니다.

→ [ADR 0004](../adr/0004-parse-on-server.md), [03-parser](03-parser.md)

### 2. `RawMessage`는 영구 보관한다

`Transaction`은 원문에서 언제든 재생성 가능한 파생 테이블입니다. 원문을 지우면 재파싱 능력을 잃습니다. 파싱 로직에 버그가 있었다는 것을 3개월 뒤에 발견해도, 원문이 있으면 전부 고칠 수 있습니다.

### 3. 파서 규칙은 코드가 아니라 DB 데이터다

카드사별 정규식을 `ParserRule` 테이블에 두고 웹 UI에서 수정·테스트합니다. 새 카드사를 추가하거나 문구 변경에 대응할 때 **배포가 필요 없습니다.**

### 4. 가시성은 세션 scope로 중앙 통제한다

화면 단에서 필터링하지 않습니다. 모든 조회가 `visibleMemberIds(session)` 하나를 거치게 해서, 감사할 지점을 하나로 모읍니다. → [07-auth-scope](07-auth-scope.md)

## 가시성 모델 요약

같은 사람이라도 **어느 화면으로 들어왔느냐**에 따라 보이는 범위가 다릅니다.

| 진입 경로 | role | scope | 보이는 것 |
|---|---|---|---|
| 앱 WebView (디바이스 토큰 교환) | 무관 | **항상 SELF** | 본인 카드만 |
| 웹 로그인 | MEMBER | SELF | 본인 카드만 |
| 웹 로그인 | **ADMIN** | **FAMILY** | **가족 전원** |

관리자도 폰에서는 본인 것만 봅니다. 폰 분실 시 피해를 본인 데이터로 한정하기 위한 설계입니다. → [ADR 0005](../adr/0005-scope-by-entrypoint.md)

## 이 설계의 한계

알림 파싱 방식에서 오는 구조적 한계입니다. 숨기지 않고 UI에 드러냅니다.

- **승인 시점 정보만 있다** — 할부 변경, 해외 결제의 환율 확정액은 늦거나 누락됩니다
- **전월실적은 추정치다** — 카드사 계산과 완전히 일치하지 않을 수 있습니다. 제외 항목 기준이 카드마다 다르고 약관에 다 적혀 있지도 않습니다
- **알림 설정에 의존한다** — 구성원이 카드사 앱에서 결제 알림을 켜고 최소 금액을 0원으로 맞춰야 합니다. 코드로 강제할 수 없습니다

보완책: Phase 6의 **명세서 대사** — 월 1회 카드사 엑셀을 올려 수집 데이터와 대조하고 누락을 메웁니다.
