# 04 — 카드 매칭

## 풀려는 문제

이 프로젝트의 목표는 **카드 한 장 단위** 집계입니다. 실적은 카드마다 별도로 쌓이기 때문에, "신한카드 이번 달 80만원"은 쓸모가 없습니다. 어느 신한카드인지 알아야 합니다.

그런데 알림에 찍히는 카드 식별자는 카드사마다 제각각이고, 마스킹되기도 합니다.

```
신한카드(1234)                  → 1234        뒷 4자리 그대로
KB국민 1*34                     → 1?34        일부 마스킹
삼성카드 ****-****-****-1234    → 1234        앞을 전부 가림
현대카드 the Green              → (숫자 없음)  카드 이름만
하나카드 승인                    → (식별자 없음)
```

마지막 두 경우가 특히 곤란합니다.

---

## 결정적으로 유리한 조건

**메시지가 어느 기기에서 왔는지 알기 때문에 `memberId`가 이미 확정돼 있습니다.**

```
RawMessage.deviceId  →  Device.memberId  →  이 사람의 카드만 후보
```

여기에 파서가 뽑은 `issuer`까지 더하면 후보군은 **"그 사람의, 그 카드사 카드"** 로 좁혀집니다. 보통 1~3장입니다.

이게 왜 중요한가: 전 국민의 카드 중에서 `1*34`를 찾는 건 불가능하지만, 아버지가 가진 신한카드 2장 중에서 찾는 건 대부분 유일하게 결정됩니다.

**후보가 1장뿐이면 마스킹이 아무리 심해도 확정됩니다.** 심지어 식별자가 아예 없어도 됩니다.

---

## 매칭 5단계

```
입력: memberId (기기에서 확정), issuer (파서), cardToken (파서, 원문 그대로)

┌─ 1. CardAlias 조회 ──────────────────────────────────
│    token 완전 일치 → 즉시 확정
│    (사람이 한 번 확정해준 표기는 여기서 걸림)
└──────────────────────────────────────────────────────
                    ↓ miss
┌─ 2. 정확 일치 ───────────────────────────────────────
│    cardToken 에서 숫자 4자리를 뽑아
│    (memberId, issuer, last4) 로 조회
└──────────────────────────────────────────────────────
                    ↓ miss
┌─ 3. 마스킹 패턴 매칭 ────────────────────────────────
│    마스킹 문자를 와일드카드로 변환 → 후보와 대조
│    정확히 1장 매칭 → 확정
│    2장 이상        → 5번으로
└──────────────────────────────────────────────────────
                    ↓ miss
┌─ 4. 별칭 매칭 ───────────────────────────────────────
│    숫자가 없으면 Card.nickname 부분일치
│    정확히 1장 매칭 → 확정
└──────────────────────────────────────────────────────
                    ↓ miss
┌─ 5. 미확정 ──────────────────────────────────────────
│    cardId = null, parseStatus = NEEDS_CARD
│    → 미확정 큐로. 사람이 지정하면 CardAlias 자동 생성
└──────────────────────────────────────────────────────
```

### 1단계: `CardAlias` 조회

가장 먼저, 가장 싸게 끝나는 경로입니다. 사람이 한 번 "이 표기는 ○○카드야"라고 알려준 것은 그대로 재사용합니다.

```ts
const alias = await prisma.cardAlias.findFirst({
  where: { token: cardToken, card: { memberId, issuer } },
});
if (alias) return alias.cardId;
```

시간이 지날수록 이 단계에서 대부분이 해결됩니다.

### 2단계: 정확 일치

```ts
const digits = cardToken.match(/\d{4}(?!.*\d)/)?.[0];   // 마지막 4자리 연속 숫자
if (digits) {
  const card = await prisma.card.findUnique({
    where: { memberId_issuer_last4: { memberId, issuer, last4: digits } },
  });
  if (card) return card.id;
}
```

`Card.last4`는 사용자가 카드 등록 시 직접 입력한 **정답값**입니다. 알림에서 온 값이 아니라 사람이 확인한 값이라 신뢰할 수 있습니다.

### 3단계: 마스킹 패턴 매칭

마스킹 문자를 와일드카드로 바꿔서 후보와 대조합니다.

```ts
const MASK_CHARS = /[*xX·●○＊•\-]/g;

function toPattern(token: string): RegExp | null {
  // 숫자와 마스킹 문자만 남기고, 마지막 4자리 분량을 취함
  const cleaned = token.replace(/[^0-9*xX·●○＊•\-]/g, '');
  const tail = cleaned.slice(-4);
  if (tail.length < 4) return null;
  return new RegExp('^' + tail.replace(MASK_CHARS, '.') + '$');
}

// "1*34"  → /^1.34$/
// "**34"  → /^..34$/
// "1x34"  → /^1.34$/
```

후보 카드들의 `last4`와 대조해서:

- **정확히 1장 매칭 → 확정**
- 0장 → 5단계 (등록 안 된 카드일 수 있음)
- 2장 이상 → 5단계 (**추측하지 않음**)

2장 이상일 때 아무거나 고르지 않는 것이 중요합니다. 엉뚱한 카드에 거래를 붙이면 두 카드의 실적이 모두 틀어지고, 사용자는 왜 틀렸는지 알 방법이 없습니다.

### 4단계: 별칭 매칭

숫자 정보가 아예 없는 경우(`현대카드 the Green`)입니다.

```ts
const candidates = await prisma.card.findMany({ where: { memberId, issuer, isActive: true } });
const matched = candidates.filter(c =>
  c.nickname && normalize(cardToken).includes(normalize(c.nickname))
);
if (matched.length === 1) return matched[0].id;
```

`normalize`는 공백 제거 + 소문자 변환입니다. 사용자가 카드를 등록할 때 `nickname`을 카드사 표기와 비슷하게 넣어두면 이 단계가 동작합니다. 관리자 가이드에 안내합니다.

**후보가 1장뿐이면 여기서 그냥 확정할 수도 있지 않나?** — 하지 않습니다. 등록하지 않은 새 카드를 쓴 경우가 있고, 그때 기존 카드에 잘못 붙으면 조용히 틀립니다. 미확정 큐에 한 번 뜨는 비용이 훨씬 쌉니다.

### 5단계: 미확정 큐

```
Transaction.cardId = null
RawMessage.parseStatus = NEEDS_CARD
```

UI에서 사용자에게 보여줄 것:

- 알림 원문
- 추출된 금액·가맹점·시각
- 등록된 카드 목록 (선택)
- **"새 카드 등록"** 버튼 — 등록 안 된 카드일 수 있으므로

사용자가 카드를 고르면:

1. `Transaction.cardId` 확정
2. **`CardAlias` 자동 생성** — `{ cardId, aliasType, token: cardToken }`
3. `parseStatus = PARSED`

다음부터 같은 표기가 오면 1단계에서 즉시 걸립니다. **이 학습 루프가 매칭 시스템의 핵심**입니다. 초반에는 미확정이 자주 뜨지만 며칠이면 거의 사라집니다.

---

## 미확정 건의 취급

미확정 거래(`cardId = null`)를 어떻게 다룰지는 집계 종류마다 다릅니다.

| 집계 | 포함 여부 | 이유 |
|---|---|---|
| 월간 총 사용액 | ✅ **포함** ("미분류 카드"로 표시) | 돈은 실제로 나갔음. 빼면 합계가 틀림 |
| 카드별 사용액 | — 별도 행 | 어느 카드인지 모르므로 특정 카드에 넣을 수 없음 |
| **실적 계산** | ❌ **제외** | 엉뚱한 카드에 실적을 붙이는 것보다 낫음 |
| 카테고리 분석 | ✅ 포함 | 카드와 무관 |

**실적에서 빼는 것이 핵심 결정입니다.** 실적은 이 프로젝트의 존재 이유인데, 잘못된 카드에 붙으면 사용자가 "달성했다"고 믿고 혜택을 놓칩니다. 모르는 것은 모른다고 두는 편이 낫습니다.

대신 미확정 건이 방치되면 안 되므로:

- 대시보드 상단에 **미확정 건수 배지**를 항상 노출
- 실적 화면에 "미확정 N건이 실적에 반영되지 않았습니다" 안내
- 관리자 가족 대시보드에서 구성원별 미확정 적체 현황 표시 (Phase 5)

---

## 카드 등록 시 주의

매칭 품질은 사용자가 카드를 얼마나 정확히 등록했느냐에 달려 있습니다. 관리자 가이드에 안내할 내용:

- **`last4`는 실물 카드를 보고 정확히** 입력 (알림에서 추측하지 말 것)
- `nickname`은 카드사 앱에 표시되는 이름과 비슷하게 (4단계 매칭에 사용)
- **같은 카드사에 뒷자리가 비슷한 카드 2장이 있으면** 마스킹 매칭이 자주 실패합니다. 이 경우 미확정 큐에서 한 번씩 지정해주면 `CardAlias`가 학습됩니다
- 카드를 해지하면 삭제하지 말고 `isActive = false`로. 과거 거래가 유지되고 후보군에서도 빠집니다

## 테스트

```
✅ "1234"           단일 후보           → 확정
✅ "1234"           후보 3장 중 1장 일치 → 확정
✅ "1*34"           후보 1장 매칭        → 확정
✅ "1*34"           후보 2장 매칭        → NEEDS_CARD (추측 금지)
✅ "**34"           후보 1장 매칭        → 확정
✅ "the Green"      nickname 일치        → 확정
✅ 식별자 없음       후보 1장뿐           → NEEDS_CARD (자동 확정 안 함)
✅ CardAlias 존재    → 1단계에서 즉시 확정 (2~4단계 안 탐)
✅ 사람이 확정 후    → CardAlias 생성되고 다음 건이 1단계에서 매칭
✅ 다른 구성원의 카드 → 후보에 절대 포함되지 않음
```

마지막 항목은 권한과 직결됩니다. 후보군 조회에 `memberId` 조건이 빠지면 아버지의 결제가 어머니 카드에 붙을 수 있습니다.
