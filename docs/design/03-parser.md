# 03 — 파서

## 이 문서의 범위

저장된 알림 원문(`RawMessage`)에서 거래 필드를 추출해 `Transaction`을 만드는 단계. 추출된 카드번호를 실제 카드에 연결하는 것은 [04-card-matching](04-card-matching.md), 취소 처리는 [05-cancellation](05-cancellation.md)에서 다룹니다.

---

## 규칙을 코드가 아니라 데이터로 두는 이유

카드사 알림 문구는 **예고 없이 바뀝니다.** 앱 업데이트 한 번에 "홍길동님"이 "홍*동님"이 되고, 구분자가 공백에서 줄바꿈으로 바뀝니다.

파싱 규칙이 코드에 있으면 그때마다 배포가 필요합니다. `ParserRule` 테이블에 두면 웹 UI에서 정규식을 고치고 즉시 반영할 수 있고, 무엇보다 **이미 쌓인 과거 원문을 새 규칙으로 다시 처리**할 수 있습니다.

→ [ADR 0004](../adr/0004-parse-on-server.md)

---

## `ParserRule` 구조

```ts
{
  id: "clx...",
  issuer: "SHINHAN",
  priority: 100,
  isActive: true,

  // 1단계: 이 규칙을 적용할지 판정
  matchPattern: "^\\[?신한카드\\]?.*승인",

  // 2단계: 명명 그룹으로 필드 추출
  extractPattern:
    "(?<holder>[가-힣*]+)님\\s+(?<amount>[\\d,]+)원\\s+" +
    "(?<installment>일시불|\\d+개월)\\s+" +
    "(?<month>\\d{2})/(?<day>\\d{2})\\s+(?<time>\\d{2}:\\d{2})\\s+" +
    "(?<merchant>.+?)$",

  // 3단계: 추출 결과를 어떻게 해석할지
  fieldMap: {
    amount:      { type: "money" },              // 콤마 제거 → Int
    installment: { type: "installment" },        // "일시불"→0, "3개월"→3
    approvedAt:  { type: "datetime_md",          // 연도 없는 월/일 처리
                   from: ["month", "day", "time"] },
    merchant:    { type: "text", trim: true },
    cardToken:   { type: "card_token" },         // 마스킹 유지한 원문 토큰
    txType:      { type: "const", value: "APPROVAL" }
  },

  // 가공된 샘플만 (불변 규칙 7)
  sampleText: "[신한카드] 홍길동님 12,000원 일시불 08/10 14:23 테스트가맹점"
}
```

`matchPattern`과 `extractPattern`을 분리하는 이유: 적용 여부 판정은 가볍게, 추출은 무겁게 갑니다. 매 원문마다 모든 규칙의 무거운 정규식을 돌리면 재파싱이 느려집니다.

---

## 추출 대상 필드

| 필드 | 필수 | 비고 |
|---|---|---|
| `issuer` | ✅ | 규칙에 이미 박혀 있음 |
| `amount` | ✅ | 콤마 제거 후 정수. **원 단위** |
| `approvedAt` | ✅ | 아래 "연도 없는 날짜" 참고 |
| `txType` | ✅ | `APPROVAL` \| `CANCELLATION` |
| `cardToken` | | 마스킹 포함 **원문 그대로**. 04 문서에서 사용 |
| `merchantName` | | 없을 수도 있음(해외·정기결제 일부) |
| `installmentMonths` | | 기본 0(일시불) |
| `holder` | | 명의자. 카드 매칭 보조에 사용 |
| `currency`, `foreignAmount` | | 해외 결제 |

### `cardToken`은 정규화하지 않는다

파서는 `1*34`를 그대로 넘깁니다. `1234`로 추측해서 채우지 않습니다. 정규화와 매칭은 [04-card-matching](04-card-matching.md)의 책임이고, 거기서 실패하면 사람에게 물어봐야 하는데 파서가 미리 추측해버리면 그 기회를 잃습니다.

### 연도 없는 날짜

한국 카드 알림은 대부분 `08/10 14:23` 형태로 **연도가 없습니다.** 그대로 두면 12월 31일 결제가 1월 1일에 업로드될 때 연도가 어긋납니다.

```
기준 = RawMessage.receivedAt (KST)

후보 연도: 기준의 연도
  파싱된 월/일이 기준보다 미래로 나오면 → 연도 - 1
  (예: receivedAt = 2027-01-01, 파싱 = 12/31 → 2026-12-31)

허용 오차: 기준으로부터 +1일 이내면 미래로 보지 않음
  (기기 시계 오차, 자정 직전 결제 대비)
```

`receivedAt`을 기준으로 삼는 것이 핵심입니다. 서버의 현재 시각이 아닙니다 — 오프라인 큐에 사흘 밀렸던 메시지는 서버 시각과 무관합니다.

## 적용 순서

> **복수 출처 선행 조건:** 같은 결제의 카드사 앱·결제 앱·카카오·SMS 원문을 거래 하나로
> 대사할 관계와 보수적 판정 규칙을 먼저 구현해야 합니다. 현재의 단순
> `rawMessageId` 1:1 upsert를 복수 출처에 그대로 적용하면 사용금액이 중복됩니다.
> 실제 원문 분석 전에는 규칙을 추측하지 않습니다. → [ADR 0007](../adr/0007-user-managed-capture-sources.md)

```
원문 도착 (parseStatus: PENDING)
  │
  ├─ 1. 무시 대상인가?           → IGNORED  (광고, 명세서 안내 등)
  │
  ├─ 2. isActive 규칙을 priority 오름차순으로
  │       matchPattern 이 맞는 첫 규칙 채택
  │       └─ 맞는 규칙 없음      → FAILED   → 미확정 큐
  │
  ├─ 3. extractPattern 으로 필드 추출
  │       └─ 필수 필드 누락      → FAILED   → 미확정 큐
  │
  ├─ 4. fieldMap 으로 변환·검증
  │       └─ 변환 실패           → FAILED   → 미확정 큐
  │
  ├─ 5. 카드 매칭 (04 문서)
  │       └─ 확정 실패           → NEEDS_CARD → 미확정 큐
  │
  ├─ 6. txType 이 CANCELLATION 이면 원거래 매칭 (05 문서)
  │
  └─ 7. Transaction upsert       → PARSED
```

**첫 매치 채택**입니다. 여러 규칙이 맞을 수 있는 경우 `priority`로 우선순위를 정합니다. 구체적인 규칙(취소 전용 등)에 낮은 숫자를 주고, 포괄적인 규칙(일반 승인)에 높은 숫자를 줍니다.

### `IGNORED` 판정

카드사 앱은 결제 알림 외에도 여러 알림을 보냅니다. 이런 것들이 매번 미확정 큐에 쌓이면 큐가 노이즈로 가득 차서 진짜 실패를 놓칩니다.

무시 대상 예시: 명세서 도착 안내, 이벤트·광고, 결제일 안내, 포인트 적립 안내

`ParserRule`에 `action: "IGNORE"`를 갖는 규칙을 두고 우선순위를 가장 높게(숫자를 작게) 둡니다.

## 실패 처리 — 버리지 않는다

파싱 실패는 정상적인 상태입니다. 새 카드사, 문구 변경, 예외적인 결제 형태에서 늘 발생합니다.

| 상태 | 의미 | 사람이 할 일 |
|---|---|---|
| `FAILED` | 규칙 없음 또는 추출 실패 | 수동 입력하거나 규칙 추가 |
| `NEEDS_CARD` | 파싱은 됐는데 어느 카드인지 모름 | 카드 지정 |

**원문은 그대로 남아 있습니다.** 나중에 규칙을 추가하고 재파싱하면 자동으로 해결됩니다.

### 미확정 큐 UI가 해야 할 일

파싱 실패 건에 대해:

1. 원문 표시
2. 수동으로 거래 입력 (`isManuallyEdited = true`로 저장)
3. **"이 문구로 규칙 만들기"** — 원문에서 정규식 초안을 생성해 편집기를 띄움
   - 숫자·날짜·금액 패턴을 자동 감지해 명명 그룹 후보를 제안
   - 사용자가 다듬은 뒤 저장하면 `ParserRule` 생성
4. 저장한 규칙을 같은 `issuer`의 다른 `FAILED` 건에 시험 적용해 몇 건이 풀리는지 미리 보여주기

4번이 실용적으로 중요합니다. 규칙 하나를 잘 만들면 밀려 있던 수십 건이 한 번에 해결되는데, 저장 전에 그걸 확인할 수 있으면 규칙 품질이 올라갑니다.

## 재파싱

규칙을 고친 뒤 과거 원문을 다시 처리합니다. **이 시스템의 핵심 복구 수단**입니다.

아래 절차는 Phase 1의 원문 1건↔거래 1건 스키마 기준 초안입니다. Phase 3에서 복수 출처
대사 관계를 결정하면 `rawMessageId` 단일 upsert를 “연결된 원문 근거 전체를 재평가하되
의미 거래는 한 번만 유지”하는 절차로 함께 갱신해야 합니다. 수동 편집 우선과 기존 거래를
파싱 실패만으로 삭제하지 않는 안전장치는 그대로 유지합니다.

```
POST /api/reparse
{
  "scope": "ALL" | "ISSUER" | "STATUS" | "DATE_RANGE",
  "issuer": "SHINHAN",           // scope=ISSUER
  "status": "FAILED",            // scope=STATUS
  "from": "2026-01-01",          // scope=DATE_RANGE
  "to": "2026-08-31",
  "dryRun": true                 // 미리보기
}
```

### 절차

```
대상 RawMessage 각각에 대해:

  1. rawMessageId 로 기존 Transaction 조회
  2. isManuallyEdited == true  →  건너뜀 (사람의 판단이 우선)
  3. 새로 파싱
  4. 성공 →  upsert (rawMessageId 가 unique key)
  5. 실패 →  parseStatus = FAILED 로 표시,
             기존 Transaction 은 삭제하지 않고 유지
```

**5번이 안전장치입니다.** 규칙을 고치다 실수로 기존에 잘 되던 케이스가 깨져도, 이전 거래는 남아 있어 집계가 갑자기 비지 않습니다. 미확정 큐에 나타나므로 문제도 곧 알아챌 수 있습니다.

### `dryRun`

실제로 반영하기 전에 결과를 보여줍니다.

```
{
  "total": 1240,
  "wouldChange": 37,
  "wouldFix": 31,        // FAILED → PARSED
  "wouldBreak": 2,       // PARSED → FAILED  ⚠️ 확인 필요
  "skippedManual": 4,
  "samples": [ ... ]     // 변경될 건의 before/after
}
```

`wouldBreak`가 0이 아니면 규칙이 기존 케이스를 깨뜨리고 있다는 뜻입니다. 반영 전에 반드시 확인하도록 UI에서 경고합니다.

## 테스트

파서는 이 프로젝트에서 **유닛 테스트가 가장 중요한 모듈**입니다. 카드사별로 아래 케이스를 최소한으로 갖춥니다.

| 케이스 | 확인할 것 |
|---|---|
| 일반 승인 | 금액·시각·가맹점·카드토큰 추출 |
| 할부 승인 | `installmentMonths` |
| 전액 취소 | `txType = CANCELLATION` |
| 부분 취소 | 금액이 원거래보다 작음 |
| 해외 결제 | `currency`, `foreignAmount` 분리 |
| 마스킹된 카드번호 | 토큰이 **원문 그대로** 넘어오는지 |
| 명의자 마스킹 (`홍*동`) | 추출 실패하지 않는지 |
| 연말연시 날짜 | 12/31 결제가 1월에 업로드될 때 연도 |
| 무시 대상 | `IGNORED`로 분류되는지 |

### 픽스처 규칙 (중요)

**실제 카드 알림을 복사해 넣지 마세요.** 가족의 거래내역이 GitHub에 영구히 남습니다. → [불변 규칙 7](../../AGENTS.md)

```
✅ "[○○카드] 홍길동님 12,000원 일시불 08/10 14:23 테스트가맹점"
❌ 실제 문자 복붙
```

가맹점명·금액·카드번호·이름은 전부 가짜로 바꾸되, **구두점·공백·줄바꿈 구조는 실물 그대로** 유지해야 테스트가 의미 있습니다. 파싱이 깨지는 지점은 대개 그 구조에 있습니다.

## 실제 문구를 보기 전에 규칙을 쓰지 않는다

**Phase 2(수집)를 완주하기 전에 Phase 3(파서)를 시작하지 않습니다.**

카드사별 알림 문구는 검색해서 알 수 있는 것이 아닙니다. 같은 카드사도 앱 푸시와 SMS와 알림톡의 형식이 다르고, 카드 종류에 따라서도 다릅니다. 추측으로 정규식을 짜면 실물이 도착했을 때 전부 다시 써야 합니다.

Phase 2의 산출물인 **"쌓인 원문"이 Phase 3의 입력**입니다.
